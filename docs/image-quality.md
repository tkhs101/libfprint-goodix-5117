# 图像质量：实测数据与结论

本文记录对"按歪就识别不了"的定量查证。
数据来自 **27c6:5117 / GF_ST411SEC_APP_12118** 上采集的真实帧，经 SIGFM 实测。

> **本文有过一次结论修正。** 第一版把一帧灰度渐变图误判为"低质量指纹"，
> 并据此认为局部均衡有效。复测匹配分数后发现该帧根本不是指纹图，
> 改动结论也随之反转。修正过程保留在第十节，供参考。

---

## 一、判定门槛有两个，不是一个

驱动侧有两道独立的门槛，容易混淆：

| 阶段 | 判据 | 位置 |
|---|---|---|
| **采集** | `sigfm_keypoints_count >= 25` | `libfprint/fp-image.c` |
| **匹配** | `match_score >= 24` | `goodix511.c` 的 `score_threshold` |

采集失败的表现：

```text
Failed to detect minutiae: No enough keypoints found
report_verify_status: result verify-retry-scan
```

**fprintd 会自动要求重按**，所以"按了没反应要重来"是预期行为。

匹配失败的表现是 `verify-no-match`——这一层不会重试，直接算失败。

---

## 二、实测帧与匹配分数

采集 4 张帧，其中 3 张是正常指纹、1 张是背景帧（详见第十节）。
先看 3 张正常帧：

| 帧 | keypoints | 自匹配分数 |
|---|---|---|
| A | 124 | 782544 |
| B | 126 | 813145 |
| C | 120 | 758429 |

自匹配分数在 **75 万–81 万**量级。

交叉匹配（同一根手指，不同次按压）：

| 帧对 | 匹配分数 | 是否通过（阈值 24） |
|---|---|---|
| A ↔ B | 8252 | 通过 |
| A ↔ C | 6 | **不通过** |
| B ↔ C | 0 | **不通过** |

**这是本轮最重要的发现：**

> 同一根手指的三次按压，只有一对能互相匹配。
> A↔B 是 8252，A↔C 只有 6，B↔C 直接是 0。

进一步测了重叠程度（用归一化互相关 NCC 找最佳位移，并对重叠面积加权）：

| 帧对 | 最佳位移 | NCC（重叠加权） | match_score |
|---|---|---|---|
| A ↔ B | dx=7, dy=-9 | **0.679** | 8252 |
| A ↔ C | dx=-4, dy=0 | **0.382** | 6 |
| B ↔ C | dx=0, dy=10 | **0.297** | 0 |

**匹配分数和重叠相关性高度一致**：NCC 0.68 能匹配，0.38 和 0.30 不能。

三帧的脊线方向分布几乎相同（水平/垂直梯度比 1.24–1.40），
所以**不是旋转问题，是位置偏移导致有效重叠区太小**。

也就是说：

> **匹配失败的主因不是"按歪"，而是手指落在传感器上的位置每次都不同，
> 两次采集的有效重叠区不够大。**

64×80 的传感器本来就小，偏几个像素就会让重叠区急剧缩小。
A↔B 只偏了 (7,-9) 就掉到 NCC 0.68；C 与两者的重叠都不到 0.4。

## 三、阈值 24 的实际含义

`score_threshold = 24` 相对实测分数来说**极低**：

- 自匹配：约 78 万
- 正常的跨帧匹配：8252
- 阈值：**24**

8252 是阈值的 344 倍，而失败案例是 6 和 0。所以匹配是"要么差得很远，
要么直接归零"的两极分布，中间几乎没有过渡带。

这解释了一个现象：**验证要么立刻成功，要么反复重试都不成功**——
不是"慢慢变差"，而是断崖式的。

## 四、几何校验是有效的（安全性确认）

用非指纹图像冒充，看会不会误接受：

| 伪造方式 | keypoints | 分数 | 结果 |
|---|---|---|---|
| 方格纹理 | 568 | 0 | 拒绝 |
| 同心圆 | 0 | 0 | 拒绝 |
| 随机噪声 | 22 | 0 | 拒绝 |
| 水平镜像 | 124 | 0 | 拒绝 |
| 垂直镜像 | 121 | 0 | 拒绝 |
| 转置 | 128 | 139197 | 接受 |

前五种全部 0 分，说明 SIGFM 的几何一致性检查（`length_match` /
角度一致性）是有效的，但转置能拿到 13 万，应该单独说明：

**转置之所以能匹配，是因为它完整保留了原指纹的脊线拓扑关系**，
相当于把指纹"旋转+镜像"了一下。真实的另一根手指不会有这种关系。
所以这不是安全漏洞，但也说明**该匹配器对整体旋转不敏感**——
这对"手指放正"是有利的，对防伪没有额外的帮助。

## 五、局部均衡：实测无效，不要合入

因为怀疑"低对比度导致 keypoint 少"，测了局部直方图均衡。
**结论是无效**：

### 自匹配分数（同一帧变换前后）

| 帧 | 原始 | 局部均衡后 | 变化 |
|---|---|---|---|
| A | 782544 | 829076 | +46532 |
| B | 813145 | 783710 | −29435 |
| C | 758429 | 731993 | −26436 |

有升有降，**没有一致收益**。

### 交叉匹配（真正重要的指标）

| 帧对 | 原始 | 局部均衡后 | 变化 |
|---|---|---|---|
| A ↔ B | 8252 | **2616** | **−68%** |
| A ↔ C | 6 | **0** | 归零 |
| B ↔ C | 0 | 0 | 不变 |

**局部均衡让本来唯一能匹配的一对，分数从 8252 掉到 2616。**

原因是清楚的：分块均衡会在块边界制造人为灰度跳变，keypoint 检测器会把这些
**伪特征**也计入。keypoint 数量看似变多（120→127 之类的微小变化），
但描述子质量下降，几何一致性更容易失败。

> **所以本文第一版里"+48 keypoints"的结论是错的**（已作废，保留于此
> 作为纠错记录），那个数字来自一张
> 背景渐变帧，而且 keypoint 多并不等于匹配好。

### 如果仍想尝试

真要评估预处理，**不能只看 keypoint 数，必须看交叉匹配分数**。
评价标准应该是：

1. 同一手指不同按压的匹配分数分布（越高、越稳定越好）；
2. 不同手指之间的分离度（越低越好）；
3. 交叉验证：留一帧做模板，其余做验证，统计通过率。

只看 keypoint 数会得出完全错误的结论——这正是本轮的教训。

## 六、那么"按歪就失败"到底是什么

综合上面的数据：

| 假设 | 数据支持？ |
|---|---|
| 按歪导致覆盖不足 | **部分**：覆盖率降到 45% 仍有 59 keypoints，采集不失败 |
| 按歪导致对比度低 | **弱**：从 124 的帧出发，对比度降到 0.35 仍有 106 |
| **按歪导致下次重叠区不足** | **强**：NCC 0.68 能匹配，0.38/0.30 不能 |
| 不同次采集特征一致性差 | 这是结果，不是原因 |

**真正的瓶颈在匹配阶段，而匹配失败的直接原因是重叠区不足。**

采集门槛（25 keypoints）其实很容易满足，三帧都在 120 以上。
失败发生在 `sigfm_match_score` 返回 6 或 0 的时候，而那正对应 NCC 只有 0.3–0.38。

## 七、多模板已经内建，而且是有效的

`libfprint` 的匹配逻辑（`fpi-print.c`）：

```c
for (int i = 0; i != template->prints->len; ++i)
  {
    SigfmImgInfo * pinfo = g_ptr_array_index (template->prints, i);
    int score = sigfm_match_score (pinfo, against);
    if (score >= score_threshold)
      return FPI_MATCH_SUCCESS;   /* 任意一个模板命中即通过 */
  }
```

登记时（`fpi-image-device.c`）每完成一帧就 `fpi_print_add_print()`，
所以**模板里天然有多帧**。本次录入 21 个阶段，模板文件 1306803 字节。

留一交叉验证（用其余帧做模板）：

| 验证帧 | 模板 | 最高分 | 结果 |
|---|---|---|---|
| A | B, C | 8969 | 通过 |
| B | A, C | 8252 | 通过 |
| C | A, B | 6 | **失败** |

**这解释了为什么实际使用中验证大多能成功**：即使某一对帧不匹配，
模板里其它帧仍可能命中。

代价是 C 这类"与谁都重叠不足"的帧无法被救回——但实际录入有 21 个阶段，
模板帧数远多于本例的 3 帧，覆盖面大得多。

> **改进方向：提高登记时的帧数或覆盖多样性**，比改预处理更直接有效。
> 当前 `goodix511` 的 `nr_enroll_stages` 决定了模板帧数。

## 八、诊断工具

`tools/diag-keypoints.c` 可以拿任意 PGM 帧做分析。

```bash
# 采集帧（注意 fprintd 沙箱，见第九节）
fprintd-verify -f right-index-finger

# 编译（libsigfm.a 是 C++，必须用 g++）
g++ -O2 -o /tmp/diag tools/diag-keypoints.c \
  -I~/src/libfprint-1/libfprint \
  $(pkg-config --cflags --libs opencv4) \
  ~/src/libfprint-1/build/libfprint/sigfm/libsigfm.a -lm

/tmp/diag /path/to/goodix-*.pgm
```

它输出每帧的 keypoints，以及在对比度下降、模糊、覆盖不足、
均衡等条件下的变化。

> 注意：**keypoint 数只反映采集质量，不反映匹配质量**。
> 评估预处理改动时，必须另外测交叉匹配分数。

## 九、帧转储的沙箱陷阱

fprintd 是 `ProtectSystem=strict` + `PrivateTmp=yes`，
`GOODIX_DUMP_DIR` **默认写不出文件**，日志只给：

```text
failed to dump image to /tmp/goodix-dump/goodix-....pgm
```

可用配置：

```ini
[Service]
Environment=GOODIX_DUMP_DIR=/var/lib/fprint/dump
ReadWritePaths=/var/lib/fprint/dump
PrivateTmp=false
ProtectSystem=full
```

**只写 `ReadWritePaths` 而不放松 `ProtectSystem` 会让服务启动失败**
（`active=failed`），因为原配置是 `strict`。

## 十、结论修正记录

第一版本文档曾给出以下错误结论，记录在此以免复发：

| 当时的说法 | 实际情况 |
|---|---|
| "某帧只有 30 keypoints，是低质量指纹" | 那帧上下半均值差 109（其他帧 10–20），是**背景渐变帧**，不是指纹 |
| "局部均衡把 30 提到 78，效果巨大" | 提升的是背景帧；对真实指纹帧，交叉匹配分数**下降 68%** |
| "按歪是主因" | 采集门槛很容易满足；失败在匹配阶段 |

**教训**：不要用 keypoint 数代替匹配质量做判断。keypoint 是采集侧的指标，
用户感知到的"识别不了"是匹配侧的问题。两者之间没有单调关系。

## 十一、下一步可以做什么

按**实测支持度**排序：

1. **提高登记帧数与覆盖多样性**（最有希望，且已在框架内）
   多模板已经生效，模板帧越多、覆盖位置越分散，命中概率越高。
   当前 21 个阶段已是较多配置，可以进一步验证"每个阶段是否真的
   采到不同位置"——如果 21 帧高度相似，等于只有 1 帧。

2. **验证重叠假说**：采集 20+ 帧，同时记录 NCC 与 match_score，
   确认"NCC < 0.4 必然匹配失败"这条线是否稳定。若成立，
   就可以在**采集阶段**提前拒绝重叠不足的帧（而不是等到匹配失败）。

3. **用标准数据集标定 SIGFM 在小图上的基线**
   量化 64×80 传感器相对标准 300+ dpi 全指图像的固有差距。
   这能回答"SIGFM 到底适不适合这个尺寸"，但不改变现网可用性。

4. **不要做的两件事**：
   - **局部均衡等预处理**：实测让匹配分数下降 68%，见第五节；
   - **盲目降低 `score_threshold`**：当前 24 相对 8252 已极低，
     再降只会让误接受风险上升而无实际收益（失败案例是 6 和 0，
     不是"23.9 差一点"）。

## 十二、给使用者的实用建议

基于以上数据，能显著提升识别率的做法是**登记时覆盖不同位置**：

```bash
fprintd-enroll -f right-index-finger
```

录入过程中，按提示移动手指——**正面、略偏左、略偏右、略偏上、略偏下**，
每个位置都按一次。因为模板是多帧匹配取最高分，覆盖位置越广，
日常随机按下的位置越容易命中某个模板。

这比反复调整按压力度更有效：实测对比度降到 0.35 都还有 106 keypoints，
但重叠不足会直接让分数归零。
